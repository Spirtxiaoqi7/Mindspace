# Mindspace 0.6 多角色架构

## 权威边界

SQLite `product_documents` 是角色和会话绑定的权威存储。文件 JSON 仅用于兼容投影与人工
检查。全局用户档案不属于任何角色；AI 档案、运行状态、头像、关系与共同经历必须属于一个
`character_id`。

`CharacterRecord` 使用 UUID、本地 revision 和 `active | archived` 状态。来源包括
`draw | custom | imported | migrated`。客户端只能请求选择角色，Core 会从已绑定会话重新
解析权威角色；含消息会话无法换绑。

## 模型输入顺序

1. 系统规则与当前角色 AI 档案。角色卡必须处于 System 权威层，不能被用户档案或当前输入覆盖。
2. 数据可信与输出契约。
3. 全局用户档案与当前角色运行状态的权威 JSON 基线。
4. 当前会话最近八轮历史。
5. 当前角色结构化长期记忆候选。
6. 当前角色其他会话的 RAG 候选。
7. 全局手动知识库候选。
8. 当前输入。
9. 最接近生成端的紧凑角色演绎校准。

历史对话不会重新全量塞入 Prompt。检索器先以 `character_id` 过滤，再做小规模词法候选，
并与当前候选一次批量向量计算。结构化记忆的 key 带 `global:` 或
`character:{uuid}:` 所有者前缀；家庭、关系、角色个性和场景记录不能跨角色返回。

## 前端路由与会话

应用每次启动从 `#/modes` 开始。`#/draw` 是抽卡工坊，`#/characters` 是典藏卡册，
`#/chat/{session_id}` 是角色已绑定的聊天页面。新建对话永远先打开角色选择器。抽卡角色的
聊天页提供重新抽卡入口；自定义角色聊天页提供前往灵感抽卡入口。

## 抽卡调用预算

抽卡生成只允许一次 `generation` 调用，没有模型协议修复。Core 清理代码围栏、校验类型并
确定性补齐缺失字段。模型 API 未配置、30 秒超时、网络错误或 Schema 无法通过时，立即使用
本地合法模板；草稿只有在用户确认收藏后才写入角色库。

## 观察与审计

Prompt Inspector 的运行记录包含 `character_id`，并明确标注 System 角色档案、全局用户与
角色运行状态、近期历史、角色记忆、角色对话召回、全局知识和当前输入的所属层。用户直接编辑角色会生成新 revision 和
`user_direct_character_edit` 审计。角色恢复、归档、复制、导入与抽卡提交均保留明确事件，
不会覆盖另一角色的档案。
