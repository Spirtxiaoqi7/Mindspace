# Mindspace 门户设计与内容规范

> 状态：Beta 门户原型规范  
> 目标读者：首次访问者、内测用户、部署者、贡献者  
> 原型：`artifacts/portal/mindspace-homepage-prototype.html`

## 1. 门户的任务

门户必须在首屏回答四个问题：

- Mindspace 是什么：本地优先的角色陪伴系统，不是通用 AI 工作台。
- 为什么选择它：关系连续、角色可迁移、工具执行可见、运行权属于用户。
- 如何开始：Windows 安装包、免安装版、源码部署三条路径。
- 它做不到什么：本地优先不等于完全离线，外部 API 与联网仍受供应商和网络影响。

门户不承担完整使用手册的职责。复杂配置、硬件要求、语音部署和开发说明应链接到对应文档。

## 2. 核心叙事

### 中文主张

**被记住，才是真正的陪伴。**

Mindspace 是一套本地优先的角色陪伴系统。角色、长期记忆、聊天场景与工具执行都由用户掌控，并可通过标准 V2 角色卡自由迁移。

### English proposition

**Companionship begins with being remembered.**

Mindspace is a local-first character companion system. You control the characters, memories, scenes, and tool execution, while standard V2 character cards keep them portable.

### 禁止使用的口径

- 不声称“完全离线”，除非模型、语音和全部能力均在本机运行。
- 不声称“支持所有模型”，应写“兼容 OpenAI 格式接口，并提供常见供应商预设”。
- 不声称工具一定成功，应写“工具请求、状态、耗时和来源可见”。
- 不声称角色会永久记住一切，应解释短期上下文、中期事件和长期召回的分层关系。
- 不把设计视图写成已经通过真实业务验收的功能截图。

- 命格设计图必须标记“设计视图”，直到真实完整旅程截图通过验收。
- 截图结束后删除临时会话，并恢复桌面原始数据运行态。

## 6. 四个产品理由

### 关系会累积

短期上下文负责本轮一致性，中期事件承接近期事项，长期召回保存跨会话关系。门户只解释层次，不宣传“记住所有内容”。

### 角色可迁移

角色权威格式采用 `chara_card_v2`。用户可以导入、导出和备份角色，不被 Mindspace 私有字段锁定。

### 能力不冒充

联网、记忆和任务操作必须经过真实工具执行。用户可查看请求、状态、耗时与来源；失败时不得声称已经完成。

### 运行权在用户

用户可使用常见 OpenAI 兼容供应商或本地兼容服务。门户不得把 DeepSeek 写成唯一支持方案，它只是推荐测试供应商之一。

## 7. 部署矩阵

| 路径 | 面向用户 | 包含内容 | 数据策略 | 门户口径 |
|---|---|---|---|---|
| Windows 安装包 | 普通内测用户 | Launcher、Core、Web、运行环境管理 | 用户选择或默认数据目录 | 推荐 |
| 免安装版 | 希望自行管理目录的用户 | 可移动 Launcher 与 Core | 数据与程序目录明确分离 | 进阶 |
| 源码部署 | 开发者与贡献者 | Python Core、React Web、桌面工程 | 通过环境变量指定运行与数据目录 | 开发 |

所有路径都不得硬编码 `A:` 盘。开发机路径只可出现在内部验收记录，不得进入 GitHub 面向用户的安装说明。

## 8. 安全与边界

- 角色、会话和记忆默认保存在用户指定的本地数据目录。
- 调用外部模型时，模型输入会发送给用户选择的 API 供应商。
- 联网检索会访问公开网页或平台接口，执行详情应显示来源与失败状态。
- API 密钥不得进入截图、日志报告、Git 提交或门户静态文件。
- 成人模式默认关闭，只能由成年用户主动开启。
- 本地语音能力受操作系统、显卡、显存、模型文件和运行环境影响。
- 删除、导入、迁移和数据目录切换必须给出可理解的确认与恢复路径。

## 11. 发布门槛

- 所有下载入口对应真实可用文件，并提供版本、大小和 SHA256。
- 首页展示版本与 GitHub 最新 Beta 保持一致。
- 三条部署路径至少各完成一次干净环境验证。
- 中文和英文页面拥有相同的信息结构与边界说明。
- 桌面与移动端截图不拉伸、不裁掉主要操作区。
- 所有外部链接通过 HTTPS，失效链接在发布前检查。
- 页面不包含测试密钥、私有角色正文、绝对开发机路径或过时模型名。

## 12. 原型到正式门户的实施顺序

1. 将静态原型拆为站点 Header、Hero、Evidence、ProductGallery、Deployment、Boundaries 和 Footer 组件。
2. 建立中英文内容文件，组件不硬编码整段产品文案。
3. 下载信息从发布清单读取，不在页面里手填版本和哈希。
4. 产品截图统一放入 `docs/assets` 或门户静态资源目录，并维护资产说明。
5. 接入链接检查、移动端截图和无障碍检查。
6. 内测通过后再把门户设为 GitHub README 的主入口。
